# CLAUDE.md

Guidance for working **on** this codebase. (User-facing install/usage lives in `README.md`.)

## What this is

`ai-image-router-mcp` — a Node/TypeScript **MCP server** (official `@modelcontextprotocol/sdk`)
that routes **image generation, image-to-video, text-to-video** across three LLM gateways
(OpenRouter, Mistral, Eden AI), plus **local background removal** (BiRefNet/ONNX), **local
animated-GIF assembly** (gifenc), **Tinify** PNG-compression/WebP, and **crop/downsize** of
images & video. ESM, strict TypeScript, Node ≥ 20.

## Commands

```bash
npm run build        # tsc -> dist/
npm run dev          # run server from source (tsx src/index.ts)
npm run typecheck    # tsc --noEmit  — run this after edits; it must stay clean
npm run trellis      # structural-debt audit (complexity/duplication/import cycles; read-only, offline). Needs **Bun** on PATH — devDependency `@os-eco/trellis-cli`, a git dep pinned to a commit (not on npm)
npm test             # node:test via tsx (tests/*.test.ts) — unit + integration, no network/cost
npm run configure    # interactive wizard -> config.json
npm start            # node dist/index.js        (stdio)
npm start -- --http  # Streamable HTTP transport (host/port from config.json)
```

Dev/test harnesses live in `scripts/` (catalog + flags: `scripts/CLAUDE.md`, loaded when working there).

## Conventions & invariants (follow these)

- **Direct REST only — never add a vendor SDK** (no openrouter/mistral/edenai/tinify packages). Hand-roll auth from token files. This is an explicit, load-bearing user requirement. (`onnx-proto` is a dependency used only by `src/bgremoval/cascade.ts` for offline ONNX graph surgery — it's lazy-`import()`ed only when a BiRefNet model is first used on WebGPU, never on the hot path. `gifenc` is a zero-dep, local GIF encoder — not a gateway SDK — used by `src/media/gif.ts`; chosen over `@skyra/gifenc` by an empirical bake-off, see the GIF gotcha below.)
- **ESM**: relative imports MUST end in `.js` (even from `.ts`). Subpath SDK imports like `@modelcontextprotocol/sdk/server/mcp.js`.
- **zod is pinned `^3.25`** for SDK compatibility — do not bump to v4.
- **stdio is sacred**: never write to stdout except the MCP protocol. All logging goes to **stderr** via `runtime.logger` (the `Logger` enforces this).
- **Tool results**: build `ToolContent[]` (`text` / `image{data,mimeType}` / `resource_link{uri,name,…}`) and return `{ content }`; on failure return `errorResult(describeError(err))` (sets `isError`), don't throw. `ToolResult` has an index signature so it's assignable to the SDK's passthrough type.
- **`possibleCause` hints on errors**: `errorResult(msg, causes?)` surfaces each cause as a standard `text` content block tagged `_meta:{'ai-image-router/category':'possibleCause'}` (`POSSIBLE_CAUSE_META_KEY`) — so any client displays it AND code can detect it by that key. `_meta` (per content block) is first-class in the SDK's `CallToolResult`. No custom content `type`, and **no `structuredContent`** (it would need a declared `outputSchema` to be idiomatic, and the `_meta` tag already makes the hints machine-detectable) — keep it this way. Causes come from the optional `Gateway.diagnoseFailure(err, {model})` hook (`types.ts`), which the tool catch blocks `await` (never throws; `.catch(()=>[])`). **OpenRouter implements it**: a data-policy/guardrail 404 → looks up the model's provider via `/models/<id>/endpoints` and suggests the **"Ignored Providers"** list; an **upstream** quota body (e.g. "You exceeded your current quota", relayed as a 200-with-`error`) while `/credits` still shows `>$0.1` remaining → suggests **"Include BYOK"** is enabled on the key, naming the key as a masked `keyIdentifier` (`sk-or-v1-cec...4c3`, never the full secret) — unless `GET /key` shows BYOK unused. OpenRouter's **own** 402 (`metadata.limit_source:"openrouter_credits"`, `isOpenRouterCreditLimit`) is never a BYOK cause (the old "balance > $0.10" guess contradicted the top-up hint on every native 402); with balance still showing it says credit is held by in-flight generations / the worst-case cost.
- **Media output**: save to `runtime.outputDir()`; return the file path as a `resource_link` (+ small inline `image` preview). Large video is never inlined. Use `mediaStem(label)` to share a stem across related files.
- **Tool registration is per-connection** (`buildServer` runs per stdio process / HTTP session), so anything derived from the config at registration time must be **re-derived on `restart`**: `refreshOnReload` (`tools/reloadable.ts`, on `runtime.onReload`) calls `RegisteredTool.update()` — the client gets `tools/list_changed`. `generate_image`'s schema is rebuilt from the new gateway+model (`buildGenerateImageSchema`), `image_to_video`'s description re-names the model, and the gated tools are **always registered but `disable()`d when they don't apply** (`registerGated` in `server.ts`): `generate_video` on **gateway capability** (so Mistral lists none), `remove_background` on a configured model. Handlers must read `runtime.gateway`/`runtime.config` **at call time** — never a gateway captured at registration (the old `gw` capture made the ICO tier pick ask the pre-restart gateway). Whether a tool is *configured* is still checked at call time. **`image_to_video` registers unconditionally** — its `output_format:"gif"` mode is local (no gateway), so it must work under any gateway; the `mp4` mode checks capability at call time and errors cleanly (pointing at the gif mode).
- **`restart` = in-process soft reload, ATOMIC** (`runtime.reload()` re-reads config, re-inits gateway, RELEASES the ONNX session — `BackgroundRemover.dispose()` → `session.release()`, since dropping the reference leaves 1–4 GB native memory alive). A remover init still loading when a restart lands is **stale** (generation counter): it never installs itself, never touches health or the newer in-flight init, disposes its session, and hands its waiters the current config's remover (`tests/runtimeRemover.test.ts`, via the `runtime.removerFactory` seam). `applyConfig(cfg)` resolves everything that can fail (gateway token, HTTP auth token, logger, gateway) into locals first and commits in one synchronous step, so a failed reload (missing token file, empty secret) leaves the previous config/gateway/tokens/auth **fully** active — never `config` describing the new setup while `gateway` is still the old one. Reload listeners fire only on success, all in one tick — `buildServer` passes `debouncedNotificationMethods:['notifications/tools/list_changed']`, so a reload sends ONE `list_changed`, not one per updated tool. **`shutdown`** flushes + exits after a short delay so the reply lands first.
- **ONNX outputs: read by declared dtype, never blind-cast.** `birefnet.ts` reads every session output through `tensorToFloat32` — it decodes a `float16` output (which onnxruntime-node hands back as a `Uint16Array` of raw fp16 **bits**) to fp32 via `half2float`, and passes a real `Float32Array` through untouched. A bare `outputs[name].data as Float32Array` on an fp16 output reads the bit patterns as integers → a silently mangled mask (a 0..1 map becomes 0..15360), which min-max then amplifies into "seams". This was the BEN2 seams bug. When wiring any new ONNX path, check the output dtype (`Tensor.type` at runtime, or decode with `onnx-proto`) and route through `tensorToFloat32`.
- **Keep `npm run trellis` low** (2/100, **0 eroded functions** after the 2026-10-04 tooling-review fixes; 4 after the 2026-10-03 cleanup and 47 before it): trellis counts any function with cyclomatic complexity **> 10** as eroded, so split a growing handler into named steps (validate → resolve → submit → render) rather than letting it accrete branches. The remaining 2 points are duplication: the `models.ts` BiRefNet catalog entries (data literals, not logic).
- Keep `npm run typecheck` clean (strict + `noUncheckedIndexedAccess`). New gateway-specific request fields go through `provider_options`/`extra` passthrough, not hard-coded per model.

`generate_image` (`generateImage.ts` + `generateImage{Schema,Request,Render}.ts`; async submit/poll via `state/generationJobs.ts`) · `image_to_video` (`imageToVideo.ts`) · `generate_video`

`transform_media` (`mediaEdit.ts`) · `build_icon_set` (`iconSet.ts`) · `health_status` + `restart` + `shutdown` (`lifecycle.ts`).

**ICO output** lives in `media/ico.ts` on top of `@fiahfy/ico` (a zero-native-dep ICO parser + builder; it embeds pure-JS `pngjs`). Three tools, three DISTINCT contracts — don't blur them:
- `generate_image` `output_format:"ico"` — **single**-entry icon: pick a model resolution ≥ `width` via `pickGenerationResolution`, then `fitSquare` (see the squaring gotcha) downscales — never upscales — keeping the untouched original as `-original.png`.
- `transform_media` `output_format:"ico"` — **multi-size / merged** icon via `buildIcoFromInputs`: each image input must already be a square allowed size (`icoSizeOfSquare` validates; **no resizing**), existing `.ico` files are `parseIco`'d and merged, duplicate sizes are rejected. Optional `sizes` = the **declared set** contract (below).
- `build_icon_set` (`tools/iconSet.ts`) — **derives** a whole declared set from one master in one call: each size is `fitToSquare`d from its assigned source (`variants[]` map specific sizes to a simplified source), emitted as its own `<stem>-<N>x<N>.<fmt>` file, then assembled and **verified** to contain exactly the declared sizes. **Nothing is written until every size is derived and the icon verified** (derive in memory → verify → write), so its "Nothing was written" errors are true — a late failure on a small variant can't leave the large sizes behind. `ico:false` emits just the images (any square size). Per-size files are encoded locally with sharp (no Tinify round-trips).

**`image_to_video` is dual-mode** (`output_format`): `mp4` (default) = AI image-to-video via the
gateway (`handleVideo` → `buildVideoResult`); `gif` = **local** animated-GIF assembly (`handleGif` →
`encodeGif` in `media/gif.ts`, no gateway, no cost). The gif mode takes ordered frames `image` →
`images_inner[]` → `image_last` (≥2; `last_frame` is a deprecated alias of `image_last`), resolves them
fail-closed via `resolveReferenceImages`, takes `fps` as a number **or per-frame array**, plus `loop` /
`max_colors` / `optimize_palette` / `fit` / `width` / `height`. `fps` is `number | number[]` in the schema;
an array on the `mp4` path errors.

Every media-returning tool takes **`output_mode`** (`filePath` default | `base64`) — built by the shared
`renderMediaContent` (`helpers.ts`); base64 always saves to disk first. `transform_media` (the former
`downsize_media`) also does format conversion (`convertImage` in `media/convert.ts` — Tinify when
enabled, else sharp) and video→still extraction (`ffprobeDuration`/`extractFrame` in `ffmpeg.ts` +
`blackFraction`/`frameBlackFraction` in `imageEdit.ts`). `image` also accepts an **array**: no-array is
batch (each processed independently, `inline_preview` forced false); with `output_format:"ico"` it builds a
multi-size/merged icon (`buildIcoFromInputs` — validate sizes, dedupe, merge); an **ICO input + non-ico image
`output_format`** (png/jpg/webp/avif) **unpacks every size** into `<stem>-<WxH>.<ext>` (`unpackIco`;
`sourceStem` from the input filename or `icon` for URL/data/base64; sharp encodes each `icoEntryToRgba` layer). Unpacking
**never overwrites**: if any name of the set exists, the whole set moves to `<stem>-2-…`, `<stem>-3-…` (`freeSetStem`); `save:false`
writes nothing (inline previews instead, when enabled).

## Gotchas (hard-won — check these before debugging)

- **sharp + 1-channel masks**: sharp processes in sRGB, so resizing a raw 1-channel buffer returns **3 channels**. Read alpha/mask with the real stride via `toBuffer({resolveWithObject:true})` + `info.channels`. (This silently broke background removal once.)
- **Animated GIF (`image_to_video` `output_format:"gif"`, `media/gif.ts`) uses `gifenc` (mattdesl), NOT `@skyra/gifenc`** — chosen by an empirical bake-off on 13 real images (full report: `output/gifbench/REPORT.md`). Why: skyra's `setQuality` is a NeuQuant **subsampling** factor (fidelity/speed) that does **NOT** move file size (size shifted ~4.6% median, non-monotonic, palette pinned ~256) — so the quality/size **knee can't exist** with it; `gifenc`'s `quantize(rgba, maxColors)` is a real palette-size axis (size rises monotonically 2→256). `gifenc` is also **zero-dep** (skyra carries tslib) and synchronous. Hard-won specifics:
  - **Buffer footgun:** `quantize`/`applyPalette` build `new Uint32Array(rgba.buffer)` **ignoring byteOffset** — feeding a sharp pooled raw-buffer *view* corrupts quantization. Always pass a **fresh exact-length** `Uint8Array` (`new Uint8Array(data)` copy; offset 0, byteLength === 4·w·h). `gif.ts` does this in `normalizeFrames`/`buildSample`.
  - **ESM trap:** no `exports` map + no `"type":"module"` → a static `import { GIFEncoder } from 'gifenc'` resolves to **`undefined`**. Load via `createRequire(import.meta.url)('gifenc')` (typed with a local interface; no `@types`).
  - **Transparency** is 1-bit only: alpha is binarized at `alphaThreshold` (default 128); quantize/applyPalette use `format:'rgba4444'` + `oneBitAlpha`; `transparentIndex` = the palette entry with `a===0`; `writeFrame` gets `{transparent,transparentIndex}`. **Global palette = pass `palette` on the FIRST frame only** (later frames omit it → reuse the global table); `repeat`/`loop` is written on the first frame (`0`=forever).
  - **Per-frame delay:** `writeFrame({delay})` is in **ms** (gifenc rounds `/10` to centiseconds). `fps` → `msFromFps` = `max(10, round(1000/fps))`. GIF granularity is 10 ms and many viewers clamp delays < ~20 ms.
  - **Palette knee** (`optimize_palette`, default on): encode across palette sizes, score each with **decode-free SSIM** (`util/ssim.ts`, luma, composited over mid-gray) — reconstruct the quantized RGBA from palette+index (LZW is lossless, no GIF re-decode needed) — **dedupe identical encodings** (gifenc collapses to the image's true color count, so several sizes coincide), then pick the max-gain elbow above the (bytes,SSIM) chord. For **high-variance/photographic** frames the knee can land aggressively low (visible banding) — use `max_colors` / `optimize_palette:false` to control; for **similar animation frames** it sits higher. `pickKnee` degrades to "smallest" when quality is flat.
- **OpenRouter image requests are built from the model's LIVE capabilities** (`src/gateways/openrouterImages.ts`; contract + live facts in `docs/API-NOTES.md` → "Per-model capabilities"). `GET /images/models/{id}/endpoints` → `supported_parameters` (typed `enum|range|boolean` descriptors; **absent key = unsupported**). `OpenRouterGateway.prepare()` (called from `runtime.applyConfig` with a 12 s bound, and by the wizard after model selection; both pass the persistent **`FileCapabilityCache`** (`.cache/capabilities.json`, git-ignored): a stored answer ≤ 7 days old is used with NO network call and refreshed in the background once older than 1 h, so only a cold start waits — stdio clients spawn a process per session, Vibe CLI per tool call) caches it so the SYNC accessors `imageAspectRatios`/`imageResolutions`/`imageQualityLevels`/`imageBackgroundModes` answer per model and the `generate_image` schema is built from them (`quality` enum appears only when advertised; `image_size` disappears when the model has no `resolution`; the `background` description states the native modes). Uncached (offline/failed) → the old static lists + optimistic sending. **`imageResolutions` returns `{values:[], source:'api'}` to mean "the API says NO resolution parameter"** — distinct from `null` ("no such concept"); the tool and wizard check `source==='api' && values.length===0`. **gpt-image-2.5 (sunburst/flare) has no `resolution`** and silently *ignores* the tier (probed: `512`→1536×1024) — so `buildOpenRouterImageBody` drops it with a note surfaced as `Note: …` in the result, and the native full-size render is stored untouched (never downscaled). Its `background` enum is **`auto|opaque` only** → `background:"transparent"` is refused **before** any request/billing (tool-level via `imageBackgroundModes`, and again in the builder), with hints to generate on a flat colour + `remove_background`, or use gpt-image-1/1-mini. `quality` (`auto|low|medium|high|xhigh|max`) is a new `ImageGenParams.quality` → body `quality`. `background:"opaque"`/`"auto"` are accepted as native **modes** (`BackgroundSpec.kind:'mode'` — no prompt constraint, nothing to verify). - **Async generation jobs (`wait:false` + `job_id`) — the fix for the MCP-client timeout**. `runtime.submitGenerationJob(kind, params, {model}, mediaOpts, render?)` runs `gateway.generateImage`/`generateVideo` in a **detached in-process task** (never `extra.signal`, so the job survives the client disconnecting) and returns a `job_id` immediately; re-invoking the same tool with `job_id` polls it until `completed`/`failed`. **Render-once:** the tool passes a `JobRenderer` (`imageJobRenderer`/`videoJobRenderer`, built from the `mediaOpts` snapshot + reference-download/constraint lines) and the runtime renders **eagerly when the job completes** (files hit disk even if nobody polls); `renderGenerationJob` memoises it (concurrent polls share one in-flight render), so every poll returns the **identical** reply — re-polling never writes duplicate files or re-bills Tinify — and the raw media bytes are dropped after rendering. A failed render keeps the result and retries on the next poll. **Failure hints:** `diagnoseFailure` runs in the background task on the REAL error object (typed `OpenRouterApiError`/`GatewayHttpError`) and the job stores `causes` + a `describeError` message — never re-diagnose from `new Error(job.error)` at poll time (the typed branches can't match). A job is bound to the gateway that **ran** it (captured at submit), not `runtime.gateway` at completion. **Memory bounds** (`GenerationJobStore`): a finished job's payload is released after **60 min** or when retained media exceeds **256 MiB** (oldest first) — the reply keeps its text + file links plus a note, inline base64 is dropped; never while a render is in flight; at most 200 finished jobs are kept. **An UNSAVED result is never released or deleted** (`isUnsavedResult`: completed, raw `result` held, never rendered, never rescued) — it is the only copy of a paid generation. When a render fails (disk, Tinify, ICO no-upscale…), the runtime **rescues** the raw media to `<stem>-unsaved-<n>.<ext>` (`rescueGenerationJob`, idempotent, best-effort); only then may the bounds drop the bytes, and the poll reply (`rescuedReply`, `isError` + resource_links) names those files. All three tools poll through **`pollGenerationJob`** (`tools/jobs.ts`), which never throws — the video tools used to call their poll outside the handler's try/catch. The provider's native job id (fal `request_id`, Eden `public_id`) is surfaced once the background task has submitted (usually by the first poll). **Jobs are in-memory only — a server restart drops in-flight jobs** (the client gets a clear "job not found" and resubmits). Configured per generation type via `config.{image,imageToVideo,textToVideo}.async` (default **true**), set by the wizard right after model selection; a per-call `wait:true`/`wait:false` overrides it. The `image_to_video` **gif mode is always synchronous** (local & instant).

It uses PramaLLC's official `BEN2_Base.onnx` (`PramaLLC/BEN2`), a **mixed-precision** graph (188 fp32 + 325 fp16 weights) whose **output tensor is declared `float16`**. ⚠️ **fp16-output footgun (this caused the BEN2 "seams"):** onnxruntime-node returns a float16 output as a **`Uint16Array` of raw fp16 bits**; reading it via a bare `… .data as Float32Array` (as the code did originally) interprets those bits as integers — a 0..1 mask becomes 0..15360 — and the min-max stretch amplifies the mangled low end into a faint **rectangular window-grid** across flat backgrounds. `birefnet.ts` now decodes by the tensor's declared dtype (`tensorToFloat32`/`half2float`): with the decode, the **same original model** produces clean masks (verified live on DML — sunken-city render + windswept-hair photo, no seams). The `onnx-community/BEN2-ONNX` repackage sidesteps it a different way (it appends a `Cast`-to-fp32 on the output so ORT hands back a real `Float32Array`); we use the canonical PramaLLC file + the decode fix instead. **Note:** the earlier conclusion that the seams were "intrinsic to BEN2's Swin window attention" was wrong — they were this dtype bug.
- **BiRefNet/bria/isnet/ben2 share the pipeline but differ per-model** (catalog in `models.ts`: `mean`/`std`/`scaleMode`/`needsSigmoid`): decode ONCE as displayed (`decodeOrientedRgb`, `bgremoval/preprocess.ts`: EXIF `.rotate()`, alpha dropped, 3 ch — the output PNG has no EXIF, so unrotated pixels made a portrait phone photo a sideways cutout; the model input AND the RGBA composite use these same pixels) → RGB → 1024² Lanczos (stretch, `fit:'fill'`), scale, `(x-mean)/std`, NCHW f32. **Scale (`scaleMode`):** rembg's BiRefNet/bria/isnet divide by the per-image **max** byte (`'imageMax'`, default); **BEN2 uses a fixed `/255`** (`'div255'`, torchvision `ToTensor`) — these differ unless the image holds a 255 byte, so it must match the training transform. BiRefNet+bria use ImageNet mean/std; isnet uses 0.5/1.0; **BEN2 uses 0/1 (no normalise)**. Postprocess: **BiRefNet output = logits → sigmoid first; bria+isnet+ben2 = no sigmoid**; then min-max → **optional hysteresis cleanup → optional `alphaFloor` black-point lift** → ×255 → resize → alpha. Read node names at runtime. **BEN2 postprocess mitigations are now OFF by default** (`alphaFloor`/`tta`/`hysteresisSeed` omitted in `models.ts`; machinery still in `birefnet.ts` + `postprocess.ts`, gated per-model + env-overridable). They existed only to fight the "seams"/haze/ghost-panels — which were the **fp16 output-decode bug** (see the seams gotcha above), not real model artifacts. With that fixed, a sweep across hair/robot/storm/sunken-city showed **raw == defaults on cleanliness (no halo on flat backgrounds), but raw keeps more fine detail** (alphaFloor + hysteresis erode hair wisps and ship rigging) **and is ~2× faster** (no TTA). So they're disabled. The three remain available per-image via env if a pathological case ever needs them: **`BG_ALPHA_FLOOR`** (black-point lift: clamp low-alpha→0 then rescale), **`BG_TTA=flip`** (average with h-mirror; ~2× inference), **`BG_HYST_SEED`** (`hysteresisCleanup`, 4-conn BFS, drops connected regions never reaching the seed confidence; "low" threshold = `alphaFloor`; caveat: can drop a *weakly*-segmented detached real subject). - **Background removal RAM guard:** CPU forward pass peaks ≈7.3 GB for BiRefNet/bria (≈25 s), ≈3.9 GB for ben2 (≈18 s), ≈1 GB for isnet (≈2.7 s) — measured via `scripts/ram-test.ts`. `requiredFreeMB` (in `models.ts`) = `usage[ep].ramMB + 512`; `BiRefNetRemover.assertEnoughRam` throws a clear "needs ~N GB free, you have Y GB" error (in `init`, the CPU-fallback branch, and before each `removeBackground`). Override: `BG_RAM_CHECK=off`. `health_status` shows free RAM/VRAM + fit — VRAM via the **async, cached** `gpuInfo()` probe (`util/sysinfo.ts`, `createGpuProbe`: one nvidia-smi query shared by concurrent callers, 10 s TTL); it used to `execFileSync` nvidia-smi twice per health call, blocking every session for up to 8 s.
- **Model download / cascade writes are crash-safe**: `ensureModelFile` streams through `stream.pipeline` (fetch body → hash/progress Transform → file) — the old hand-rolled write loop left a write error with no listener (uncaughtException on the startup pre-warm path) or hung forever awaiting `finish` from an errored stream (July M9, reproduced in `tests/modelDownload.test.ts`); the `.part` is removed on failure. `cascadeWideOps` writes `<model>-webgpu.onnx` via temp file + rename, because the runtime reuses that file forever once it exists.
- **Tinify** is 2 requests: `POST /shrink` (raw body, Basic `api:key`) → `Location`; then `GET <Location>` (compress) or `POST <Location> {"convert":{"type":"image/webp"}}` (convert). `generate_image` always coerces to PNG first (`ensurePng`). **AVIF** is a Tinify `convert` type (`image/avif`, confirmed live) — `generate_image` `output_format` and `convertImage` both support it; Tinify ingests only png/jpeg/webp/avif (other rasters get `ensurePng`'d first).
- **`output_mode` & binary**: MCP can't stream raw bytes — stdio is newline-delimited UTF-8 JSON-RPC, tool results are one JSON object, binary is only base64 (`image`/`audio` data or `resource` blob). So `output_mode` is just `filePath | base64` (no `Uint8Array`); for raw local bytes a client reads the saved file. `renderMediaContent` (`helpers.ts`) builds it: base64 image → `image` block, base64 video → embedded `resource` blob. base64 always saves to disk first.
- **`transform_media` PNG-base64 rule**: returning a not-yet-Tinified PNG as **base64** while Tinify is enabled → keep the uncompressed file as `<stem>-original.png`, Tinify-compress in place, return the compressed bytes. (Distinct from **video→still** extraction, which Tinify-optimizes the PNG **in place with no `-original`**.)
- **One magic-byte detector: `detectMedia` (`util/mime.ts`)** → `{kind:'image'|'video'|'document', mime}` | null. `detectImageMime` (validation: null = refuse), `sniffImageMime` (provider output without a mime: detected else `image/png` — never use it to validate), and `sniffKind` are all built on it; it replaced five sniffers whose drift sent AVIF to a provider as `image/png` and classified every ISO-BMFF `ftyp` (AVIF/HEIC) as video. ISO-BMFF: the major AND compatible brands are scanned (`avif`/`avis` → AVIF, `heic`/`mif1`/… → HEIC, else mp4/quicktime); EBML doctype → webm vs mkv; BMP needs a real DIB-size field (a bare "BM" matched text). `resolveMediaInput` classifies data: URLs and downloads by bytes first (declared mime/content-type only for unrecognised bytes). Add a format HERE, once.
- **`transform_media` `output_format:"mp4"` on a video transcodes** (`transcodeToMp4`; an mp4 passes through) — it used to fall through to the passthrough and return the .webm/.mkv unchanged. ffmpeg's shared `ENCODE` re-encodes audio to **AAC** (`-c:a copy` fails for PCM/Vorbis in an mp4), for crop/downsize too. `MIME_EXT` knows mkv/avi/bmp/tiff/heic, so a passthrough keeps its real extension. `save:false` writes nothing for `transform_media` ico builds and `image_to_video` gif (incl. no `z-download-` frame copies).
- **Video→still** (`transform_media`, video input + image `output_format`): samples from **10% of duration**, stepping +5% up to 95% (18 tries) past frames that are ≥90% black (luma < 32, via `frameBlackFraction`), falls back to the 10% frame. Needs `ffprobe` (ships with ffmpeg). The whole search runs over ONE temp copy of a byte-only video (`withVideoFile`); each primitive used to write and delete its own copy (up to 19× the video). Image input + a video `output_format` → error pointing at `image_to_video`.
- **Format conversion engine**: `convertImage` uses **Tinify when a token is set, else sharp** (sharp handles png/jpg/webp/avif locally — AVIF encode works in the bundled libvips). So conversion still works with no Tinify key, just larger files. ⚠️ **Tinify's compress (`GET <Location>`) is FORMAT-PRESERVING**: "jpg → png" via compress returned the same JPEG bytes under a `.png` name. A non-PNG source is re-encoded to PNG with sharp before compressing, and every Tinify answer's magic bytes must match the target (`assertProduced`, else the sharp fallback runs).
- **`downsizeImage` fits INSIDE width×height** (`fit:'inside'`): sharp's default fit is `cover`, so with both dimensions it center-CROPPED to the box. Video downsize already used `force_original_aspect_ratio=decrease`. `cropImage` checks the region against the image bounds first (libvips only says "bad extract area").
- **Windows ICO broadcast (`.ico`)**: encoded via `@fiahfy/ico` (zero native deps — embeds `pngjs`), NOT `png2icons`/`icojs`/`to-ico` (those hardcode one size set, always resize to 9 canonical sizes, or can't merge). Every entry is written as a classic **32-bpp BMP/DIB + AND mask** (the most broadly-compatible form — readable Windows 98 → XP → Vista → 11, Linux, macOS) rather than a PNG-compressed entry (Vista+ only, blank on Win98/XP). `Ico.supportedIconSizes` is a mutable static array — widen it with `.splice()` (it's `readonly` on the reference, so don't reassign) to the allowlist `16,20,24,32,40,48,64,72,96,128,256`. Reuse `media/ico.ts` helpers; don't call `@fiahfy/ico` directly from the tools.
- **ICO = three distinct size contracts**: `generate_image` ico **resizes ONE image** (target `width` is the desired square output; the model renders at the closest supportable size ≥ width via `pickGenerationResolution` over `gw.imageResolutions(model)` — **per-model**, not per-provider — or at exact `width×width` where the model accepts object `image_size`; then `fitSquare` squares + downscales, never upscales, and keeps the untouched original as `-original.png`). The render is **square by default**: without an explicit `aspect_ratio`/`height`, ico uses `height = width` and `aspect_ratio:'1:1'` (`squareAspectFor` — when the model takes 1:1) instead of the configured default aspect (often 4:3, which used to request 256×192 and letterbox the icon). `transform_media` ico **validates, doesn't resize** (each image input must already be a square allowed size via `icoSizeOfSquare`; existing `.ico` files are parsed and merged; no `width`/`height` allowed). `build_icon_set` **derives a whole declared set** (many sizes from one master + optional per-size `variants`). Don't blur these three.
- **Squaring never crops silently (`fitSquare`/`fitToSquare`)**: the default `fit` is **`pad`** — the whole image is contained on a square canvas (transparent, or `background` hex) — because the old center-crop deleted off-centre subjects outright (a 1280×720 render with the subject near the left edge lost it completely; the icons looked "empty"). `crop` is still available and reports how much it dropped. The functions return `{bytes, applied:'none'|'pad'|'crop', sourceWidth, sourceHeight, note}` — **surface `note` in the tool result** so squaring is never invisible. No-upscale rule differs per mode: `crop` needs `min(w,h) ≥ size`, `pad` only needs `max(w,h) ≥ size`.
- **Declared size set (`transform_media` ico `sizes`)**: without it the tool embeds whatever the inputs happen to be and reports the sizes it got — which is how a "4-size" icon silently became 7. With `sizes` the emitted entries must equal the declared set exactly (else error, nothing written); when `sizes.length === inputs.length` the check is **positional** — each input must actually BE its declared size, and a mismatch names the offending element. Provenance (`16x16 ← favicon.ico (embedded entry)`) is always reported, declared or not.
- **Structured generation constraints (`media/palette.ts`)**: `palette` / `exclude` / `background` on `generate_image` are compiled ONCE (`compileConstraints`) into a deterministic prompt block appended to the prompt (so the constraint reaches every gateway) **and** carried as structured `ImageGenParams` fields so gateways map them natively: fal Recraft `colors[]`/`background_color` (the only fal palette input — `colorFields` in `falModels.ts`), `negative_prompt` (Cosmos/FLUX/Ideogram), OpenRouter `background` (enum `auto|transparent|opaque` ONLY — a hex would 400, so a colour maps to `opaque` and the hex stays in the prompt). Exclusion terms are expanded ("text" → "text, letters, words, numbers, labels, captions, typography, logotype") and the hue families NOT covered by the palette are named as forbidden ("no blue…"), which is the nagging callers used to type by hand. Results are then MEASURED (`analyzePalette` on saturated/opaque accent pixels, `analyzeBackground` on the border ring) and reported — a malformed hex fails before the model is called.
- **Reference semantics are per-model and NOT interchangeable** (`Gateway.referenceSemantics(model)`): `subject` conditions on the reference's object/geometry (OpenRouter `input_references`, fal `flux-2-pro/edit` `image_urls`), `style` transfers its look/medium (fal Krea `image_style_references` — feed it a photo and the output looks like that photograph). `generate_image`'s `reference_mode` picks one; an unsupported mode is refused **before** the request (naming the field + a model that can do it), and a supported-but-not-native mode is honoured by a prompt steer. The schema deliberately accepts BOTH values so the handler can return that useful error instead of a raw zod enum dump. `health_status` states the configured model's semantics.
- **fal per-model specs (`gateways/falModels.ts`) — the size/reference map.** There's **no one-size-fits-all fal request shape**. FLUX-family (Flux 2 Pro, Flux Pro, Flux LoRA, Flux/Krea, Flux/dev, Flux/schnell) and Recraft and Cosmos take `image_size` = an object `{width,height}` (exact pixels, max 14142, unsigned) **or** an enum tier (`square_hd`/`square`/`portrait_4_3`/`portrait_16_9`/`landscape_4_3`/`landscape_16_9`). Krea 2 and Ideogram take `aspect_ratio` = a ratio enum (no exact pixels). `output_format`/`enable_safety_checker`/`safety_tolerance` exist **only on some models** (FLUX: all three; Cosmos: `output_format`+`enable_safety_checker`; Recraft: `enable_safety_checker` only; Krea/Ideogram: none). `falImageSpec(model)` resolves all of this; `buildFalImageInput` sends the seeded defaults **only to models that read them** and uses object `image_size` when `width`/`height` are given. **The old `isKrea` regex was too broad** (it matched `fal-ai/flux/krea`, which takes image_size not aspect_ratio) — the spec map replaces it.
- **fal `reference_images` hard-fail before credits**: no fal **text-to-image** model has a conditioning input except Krea 2 (`image_style_references[]`, style-only) and FLUX 2 Pro's separate **Edit** endpoint (`image_urls[]`). `buildFalImageInput` throws before `runQueue` (so no generation is billed) if `references` are passed to any model without a reference field. The tool-level `imageReferenceImages` capability stays `true` (some models do take them); the per-model gate is authoritative. **Krea's `image_style_references[]` item shape is `{ image_url, strength? }`** (NOT `{ url }` — a fixed bug; `image_url` required, `strength` −2…2 default 1). Live-validated on `krea/v2/medium` + `krea/v2/large`.
- **`generate_image` size params are `width`+`height`**: `ico_size` was renamed to `width` (a general pixel size, not ico-only). `height` derives from `width` × `aspect_ratio` (`aspectRatioValue`) unless given. For ico, `width` must be an allowed ICO size (else rejected before generation). Doorway object `image_size` is built in `fal.ts` (`resolvedSize`) from `width`/`height`.
- **ICO READING is our own `parseIco` (`media/ico.ts`), NOT `@fiahfy/ico`'s** — that parser only handles 32-bpp DIB entries (its `IcoInfoHeader.from` throws "Only 32 bpp supported" and `IcoImage.from` reads a PNG entry's signature as a BITMAPINFOHEADER → width ≈ 169 million), so a typical Vista+ favicon (PNG-compressed 256 entry + 8/24-bpp small sizes) failed to merge/unpack. `parseIco` is **async** (PNG entries decode via sharp) and returns `IcoEntry {width,height,encoding:'png'|'dib',bitCount,rgba}` (top-down RGBA); it handles 1/4/8-bpp palettes, 16/24/32 bpp, the AND mask (alpha for <32 bpp, and for legacy 32-bpp entries whose alpha channel is all zero), the doubled DIB height, bottom-up/top-down rows, and refuses truncated/implausible entries before allocating. Merging re-encodes each entry through the same 32-bpp writer (`icoImageFromEntry`). `@fiahfy/ico` is still the ENCODER. `icoPreviewContent` (helpers.ts) renders the largest entry to PNG for inline previews (sharp can't decode ICO). An ICO is recognized by `isIcoSignature` (`util/mime.ts`: `00 00 01 00` + count > 0 + a plausible first directory entry — 4 bytes alone also start MPEG start codes); `MIME_EXT` maps `image/x-icon` → `.ico`. Hand-built real-world fixtures (`rawIco`/`dibEntry`) live in `tests/ico.test.ts`.
- **`generate_image` ico `ico_size` schema**: it's a numeric literal union, not a `z.enum` (zod enums are string-only). Build via `z.union(ICO_ALLOWED_SIZES.map(s => z.literal(s)))` with a 2-ELEMENT tuple cast.
- **`output_format:"ico"` is offered even without a Tinify key** (a local container, no optimizer); the non-ico formats (png/jpg/webp/avif) remain gated on `tinifyEnabled`. So `format` now resolves `ico` first, then falls back to tinify-gated formats.
- `ffmpeg` is expected on PATH only for **video** crop/downsize; absence returns a clear error (image editing is unaffected). It IS available in this dev environment (useful for frame extraction / ffprobe).
- **Bg-model startup pre-warm + onnxruntime stderr noise**: `index.ts` kicks off `runtime.getRemover()` after the transport connects (non-blocking) so the first `remove_background` isn't delayed by a ~970 MB session load. That means **every** server spawn loads the ONNX model — wasteful for short-lived introspection. Set **`BG_NO_PREWARM=1`** to skip it (still lazy-loads on first use); `list-tools.ts` sets this when spawning. Separately, onnxruntime's **native lib logs its own warnings straight to stderr** (`Removing initializer …`/CleanUnusedInitializers, "Some nodes were not assigned to the preferred EP", lenient shape-merge) — they bypass `runtime.logger` and look like errors but are benign. Silenced via `logSeverityLevel: 3` on `InferenceSession.create` (`birefnet.ts`); real Error-level failures still surface (and we catch+log EP fallback ourselves).
